# Refactoring

## Overview

Refactoring, a term Kaufman borrows from software engineering, is changing the internal structure of a system without changing what it produces for the outside world — same output, better mechanism. It is distinct from optimization, which pushes a given structure to perform better on a metric; refactoring reorganizes how the work is done so the system becomes simpler, cheaper to run, or easier to change, while the customer sees no difference in the result. A business that has grown by accretion accumulates the operational equivalent of tangled code — redundant approval steps, workarounds layered on workarounds, three tools doing one job — and refactoring is the deliberate cleanup: consolidating the tools, removing the dead process, straightening a workflow that grew crooked. The discipline is to improve the structure while holding the output constant, so you can verify you changed only how the system works, not what it delivers.

## Context & Usage

Refactor when a system still produces acceptable results but has become unwieldy, expensive, or resistant to change — when every new request requires heroics because the underlying structure is a mess. Do it in small, verifiable steps, checking after each that the output is unchanged, so you never confuse a structural cleanup with a change in what customers receive. It's how you pay down accumulated "process debt" before it strangles the ability to grow or adapt (Change, 542). Because refactoring simplifies, it often makes a system healthier in the Gall's Law (532) sense — a leaner structure is easier to keep working and extend. When cleanup isn't enough and the structure is fundamentally wrong, the more radical move is a rebuild from a simpler base rather than continued refactoring.
