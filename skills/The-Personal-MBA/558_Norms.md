# Norms

## Overview

A Norm is the typical, expected value or pattern for a system — what "normal" looks like — and Kaufman's point is that establishing norms is what makes it possible to recognize the abnormal, which is where nearly all useful signals hide. A single measurement is inert; measured against the norm, it becomes information, because meaning lives in the deviation. You can only tell that today's sales are alarmingly low, that this month's churn spiked, or that a server's response time is off if you know what normal has been. Norms come from history (your own past pattern) or from benchmarks (what's typical for comparable operations), and they are what let a dashboard flag "something is wrong here" rather than just displaying numbers. Establishing a norm also forces you to gather a baseline before you need it — you can't spot an anomaly against a reference you never recorded.

## Context & Usage

Build norms deliberately for the metrics that matter: track them long enough to know their normal range and typical rhythm, including seasonal or weekly cycles, so a genuine deviation stands out from ordinary fluctuation. Use them as tripwires — set expected ranges and investigate when a value falls outside, rather than staring at raw feeds hoping to notice something. Be careful not to normalize a bad baseline: a norm describes what is usual, not what is good, so a consistently poor process can look "normal" and escape scrutiny. Norms operationalize Context (552) over time and are the reference point KPIs (549) are read against.
