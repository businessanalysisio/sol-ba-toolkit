# Gall's Law

## Overview

A complex system that works is invariably found to have evolved from a simple system that worked — and, just as reliably, a complex system designed from scratch never works and cannot be patched into working; you have to start over with a simple system that does. Kaufman borrows John Gall's observation as a warning against grand, all-at-once builds. Complexity that survives is grown, not blueprinted: each layer is added only after the layer beneath it is proven, so the working relationships between parts are discovered by operating the system, not imagined in advance. The canonical move is to launch the smallest thing that actually functions — a single-page site that takes one order, a spreadsheet before an ERP, one manual delivery route before a logistics platform — and let it earn its next feature. Ambitious redesigns that try to specify every interaction up front routinely collapse under their own untested assumptions.

## Context & Usage

Apply this the moment someone proposes a big, fully-featured system as the starting point — a two-year platform rebuild, a process that handles every edge case before handling any case. Insist instead on a working core that delivers real value now, then accrete. It is the systems-level justification for MVPs, pilots, and phased rollouts: you are not just reducing risk, you are respecting the fact that the working configuration is unknowable until the simple version runs. When an existing complex system is failing and resisting every fix, Gall's Law says stop patching and rebuild from a simpler base that works.
