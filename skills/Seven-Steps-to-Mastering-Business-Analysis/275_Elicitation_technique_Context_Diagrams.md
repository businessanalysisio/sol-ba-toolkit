# Elicitation technique: Context Diagrams

## Overview

One circle for the system or project under study, boxes around it for every external entity — people, departments, other systems, regulators, vendors — and labeled arrows for each flow of information crossing the boundary. That is the whole notation, inherited from structured analysis, and its poverty is its power: a context diagram fits on one page, executives and developers read it identically, and drawing it with stakeholders is itself elicitation. Every arrow is an interface someone must specify; every entity is a stakeholder someone must consult; and the boundary line is the scope decision made visible — the argument about whether the billing system is inside or outside the circle is exactly the argument the project needs to have in week one rather than month six. Carkenord favors it as the diagram that catches missed stakeholders and missed interfaces before they become missed requirements.

## Context & Usage

Draw it at initiation to accompany the scope statement (270), and redraw whenever scope changes — an out-of-date context diagram is worse than none because people trust it. Work outward: list entities first, then flows in each direction; a one-way arrow to an entity that sends nothing back is often a clue something is missing. Keep it at context level — the temptation to decompose the circle into internal processes turns a scoping tool into a modeling project.
