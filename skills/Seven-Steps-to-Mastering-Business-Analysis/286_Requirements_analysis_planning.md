# Requirements-analysis planning

## Overview

Before analyzing anything, decide how you will analyze: which deliverables and models this particular project needs (a data-heavy conversion wants data models and a dictionary; a workflow redesign wants process maps; a small enhancement may want one page of well-formed requirements and nothing else), which elicitation techniques in which order, who reviews and who approves each deliverable, and how requirements will be stored, traced, and change-managed. Carkenord frames the plan as tailoring against three dials — project size, risk, and methodology — with the cardinal sin being the template reflex: producing every artifact the organization's standard lists because the standard lists it. Each planned deliverable should answer "who consumes this, for what decision?"; a model with no consumer is planned waste. The output doubles as the BA's answer to the PM's scheduling question — here is what business analysis will produce, in what sequence, needing which stakeholders when — which is what makes BA effort visible and defensible on the project plan.

## Context & Usage

Draft it at project start alongside stakeholder analysis (263), negotiate it with the PM and sponsor, and revise as discovery changes the picture — a plan that survives elicitation untouched was not paying attention. On agile projects the plan shrinks to conventions (definition of ready, story format, refinement cadence) but the same decisions get made. Estimation (288) hangs off this plan: you can only estimate analysis work you have first named.
