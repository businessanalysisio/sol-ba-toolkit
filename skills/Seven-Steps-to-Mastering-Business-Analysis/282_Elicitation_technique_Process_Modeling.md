# Elicitation technique: Process Modeling

## Overview

Used as elicitation, the diagram matters less than the drawing of it: put a swimlane skeleton on the wall — one lane per role or system, boxes for tasks, diamonds for decisions, arrows for handoffs — and build it live with the people who do the work. The model's demands generate the questions automatically: every decision diamond forces "on what rule do you branch, and who owns that rule?"; every handoff across lanes forces "what exactly passes, and how does the receiver know it arrived?"; every path must end somewhere, which flushes out the exception flows ("and what happens when the credit check times out?") that narrative elicitation never volunteers. Disagreements that stay hidden in interviews become visible when two SMEs reach for the same marker — which is the point. Validation is a scenario walkthrough: take a real case and trace it box by box; where the case leaves the model, the model is wrong.

## Context & Usage

The default technique for cross-functional workflows, handoff-heavy operations, and any project whose subject is "how work flows" rather than "what data means." Choose altitude deliberately — a high-level map for scope conversations, detailed flows only where the project will change the process — and resist modeling the whole enterprise because the notation is enjoyable. Works for both as-is capture (283) and to-be design, ideally as two explicit models so the gap between them can be read as the change the project must deliver.
