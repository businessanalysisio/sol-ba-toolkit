# Using team-collaboration tools effectively

## Overview

The tool question that matters for a BA is not which product but which channel for which job: a live shared whiteboard for co-creating models, threaded async discussion for questions that need thought, a document repository with versioning for deliverables, and a tracker for open issues and decisions — with one non-negotiable rule Carkenord implies throughout: requirements live in exactly one place. The moment requirement text is duplicated into email threads, slide decks, and chat messages, the copies diverge and stakeholders review different truths. Effective use also means explicit team norms: where decisions get recorded, naming and version conventions, who is expected to respond to what, and restraint with notifications so the important ones still get read.

## Context & Usage

Set the tool conventions at project kickoff, jointly with the PM, and write them down — a one-page "where things live" note saves weeks of archaeology later. Distributed teams (266) depend on this doubly, since the tools replace the hallway. Resist the urge to adopt a new tool mid-project because a feature looks appealing; migration costs and split history usually outweigh it. And remember tools capture but do not create shared understanding: a wiki page nobody discussed is documentation, not agreement.
