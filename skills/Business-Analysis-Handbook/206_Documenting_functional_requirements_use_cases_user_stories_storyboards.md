# Documenting functional requirements (use cases, user stories, storyboards)

## Overview

Functional behaviour can be captured in several forms, each with a distinct centre of gravity. Use cases specify actor–system interaction rigorously: actor, goal, preconditions, main success scenario as numbered steps, alternate and exception flows, postconditions — the exception flows being where most of the analytical value (and most of the defects avoided) lives. User stories ("As a... I want... so that...") slice behaviour into small, independently deliverable increments, with the real substance carried by their acceptance criteria; they suit iterative delivery and continuous conversation, not archival completeness. Storyboards narrate a user's journey visually across screens and touchpoints, exposing experience gaps that stepwise formats hide. The forms combine well — an epic-level use case decomposed into stories, a storyboard illustrating the journey the use cases formalise — provided granularity stays consistent within any one catalogue.

## Context & Usage

Choose the form by delivery method and audience: use cases for contract-style specification, complex multi-actor logic, and vendor handoffs; stories for agile teams refining scope sprint by sprint; storyboards when stakeholders need to feel the future state before committing to it. Whatever the format, every functional requirement still needs a home in the hierarchy (201) and a link into traceability (214) — format is presentation, not governance.
