# Techniques and documentation (translating agreements into clear, detailed written artifacts)

## Overview

Verbal agreement evaporates; the BA's job is to fix it in artifacts precise enough that a developer can build from them and a tester can test against them. That means choosing the artifact that fits the content — a swimlane process map for who-does-what, a use case for actor–system interaction, a data dictionary for field-level meaning, a decision table for complex rules — rather than forcing everything into prose. Craft rules apply regardless of form: unambiguous wording, one fact per statement, unique numbering so items can be referenced in reviews and traceability, a glossary for contested terms, version control with a change history, and detail calibrated to the audience (an executive summary is not a diluted spec; it is a different document).

## Context & Usage

The bridge activity between elicitation and delivery: used immediately after workshops and interviews, while agreements are fresh, and continuously as the requirement set matures toward baseline. Poor documentation is where good analysis goes to die — if stakeholders agreed in the room but the write-up is ambiguous, the disagreement simply resurfaces in testing, at ten times the cost. When a stakeholder disputes a documented point, treat it as a win: the artifact did its job of exposing the mismatch early.
