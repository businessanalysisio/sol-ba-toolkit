# Process-map notation and symbol standards

## Overview

A process map is only useful if a reader who wasn't in the workshop can decode it, which makes notation discipline a practical skill rather than pedantry. The core flowchart vocabulary: rounded terminators for start and end points, rectangles for tasks, diamonds for decisions (each exit labelled with its condition — yes/no, or the actual business rule), arrows for flow direction, and off-page connectors when a process continues elsewhere. Swimlanes bind every step to the role, team, or system that performs it. Formal standards such as BPMN add richer semantics (events, gateways, message flows) suited to process automation work, but a business audience is usually better served by a small consistent symbol set than by full BPMN. Whatever the choice: include a legend, follow the house standard if one exists, keep flow direction consistent (top-down or left-right), and never invent a new symbol mid-document.

## Context & Usage

Applied every time a process is drawn, and especially when maps will outlive the project — entering a process repository, feeding a BPM tool, or serving as operational documentation. Consistency across a map set is what lets stakeholders compare as-is and to-be diagrams without relearning the vocabulary each time. When inheriting maps from others, translate them into the standard before analysis; symbol ambiguity ("is that diamond a decision or an approval?") silently corrupts findings.
