# Requirements organisation

## Overview

Structures a raw haul of elicited requirements into a coherent set before documentation is finalised. Two structuring moves dominate. First, classification by type: general requirements (business policies and constraints — legal, regulatory, branding, cultural), technical requirements (platform, interfaces, environment), functional requirements (what the solution must do), and non-functional requirements (how well — performance, availability, security, usability, capacity). Second, hierarchy: broad business requirements decompose into stakeholder-level requirements and then into detailed solution requirements, so each detailed item can point upward to the need that justifies it. Along the way the analyst filters the set — merging duplicates that arrived from different stakeholders in different words, surfacing conflicts for resolution by the owners, and flagging out-of-scope wishes.

## Context & Usage

Performed as elicitation output accumulates, and worth doing before validation reviews: reviewers confronted with 400 unsorted statements find nothing, while a typed, levelled catalogue exposes gaps by category ("no security requirements at all?") and duplication by grouping. The chosen structure also becomes the navigation scheme of the requirements document and the grouping key for prioritisation and release planning. Resist inventing exotic taxonomies — the value is in consistency, not cleverness.
