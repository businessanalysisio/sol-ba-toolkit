# Problem solving

## Overview

A disciplined path from "something is wrong" to a verified fix, resisting the organizational instinct to jump straight to a favorite solution. The sequence matters: define the problem precisely first — PMI's situation statement format (problem X has effect Y with impact Z) forces quantification before ideation — then trace symptoms to root causes, since "invoices go out late" may bottom out in a master-data ownership gap three departments away from invoicing. Only then generate options, deliberately more than one, and only then evaluate. The closing discipline is verification: after implementation, did the metric named in the situation statement actually move? A solved problem is a measured claim, not a shipped feature.

## Context & Usage

Problem solving is effectively the skeleton of PMI's Needs Assessment domain — situation statement, root cause or opportunity analysis, option identification, recommendation. It re-emerges inside Requirements Elicitation & Analysis whenever a modeled process reveals a defect worth fixing rather than automating, and in Traceability & Monitoring when a flood of change requests signals a problem that was never correctly defined. Solution Evaluation is its feedback loop: unverified fixes are how organizations solve the same problem annually.
