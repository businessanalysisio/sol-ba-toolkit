# Data / functional / operational / systems / UX analyst

## Overview

A cluster of specialist titles that are each business analysis scoped to one layer of the solution. The data analyst owns definitions, quality rules, and lineage — what "customer" means across five systems that disagree. The functional analyst specifies system behavior: inputs, validations, outputs, and what the screen does when the payment gateway times out. The operational analyst covers the human side of run-state: procedures, handoffs, staffing implications, cutover readiness. The systems analyst works the seams — interfaces, message contracts, integration sequencing. The UX analyst grounds requirements in observed user behavior: research sessions, personas, task flows, wireframes tested before a line of code. On sizeable programs these are different people whose outputs must reconcile; on small ones a single BA rotates through all five hats, and the checklist value of the list is knowing which hat you have not yet worn.

## Context & Usage

PMI groups these under the roles that perform business analysis, and all of them live mainly in Requirements Elicitation & Analysis — each specialization corresponds to a family of the guide's analysis models (data dictionaries and ERDs, use cases, procedures, interface models, prototypes and personas). Traceability & Monitoring is where the layers must join up: a data attribute traces to the screen that captures it, the interface that transmits it, and the procedure that corrects it. Gaps between specialist views are a classic source of defects found only in integration testing.
