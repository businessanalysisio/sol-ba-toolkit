# Requirements manager

## Overview

The custodian of the requirements set as a managed asset — a role that emerges on large programs where several BAs, hundreds of requirements, and multiple vendors make ad hoc stewardship collapse. BA work manifests as governance rather than elicitation: defining the attribute schema every requirement must carry (unique ID, source, owner, priority, status, verification method), establishing baselines so "version 2.1 of the requirements" is a precise statement contracts can reference, operating the change control process — logging each request, ensuring impact analysis happens, routing it to the right approval authority, propagating approved changes through every affected artifact — and keeping the traceability matrix alive as requirements move through design, build, and test. The role's quiet KPI is auditability: at any moment, being able to answer which requirements are approved, which changed since baseline and why, and which remain unverified.

## Context & Usage

PMI includes the requirements manager among roles performing business analysis, and Traceability & Monitoring is its native domain — the guide's material on baselining, requirement life-cycle states, and change management describes this job. Business Analysis Planning is where the requirements manager earns leverage, designing the repository, attributes, and approval workflow before volume arrives; retrofitting governance onto ungoverned requirements is far costlier. The role supplies Solution Evaluation its foundation, since only a governed requirement set makes "did we deliver what was approved?" answerable.
